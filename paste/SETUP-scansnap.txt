Scan snap checkboxes — what to paste.

The staff page already shows Scan snap and Mobile. Both boxes start checked. Until this paste is deployed, the page says changes are not saved yet, and unchecking does nothing on the server.

The QR tag (JO sticker) prints when the scan is filed. The jewelry tag queues after you confirm the JO, so the tag can read the name, weight, metal, and stones from JobOrders. A field still marked (guess) is left blank. It is not printed with the mark stripped off.

Replace the whole script (code only)
  Apps Script: open ScanSnapPrint, replace it with paste/ScanSnapPrint.gs (the whole file).
  Save. Do not run a setup function. The first filed scan creates a SnapSeen tab (columns id, at) if that tab is not already there. Each JO + jo_card + scan file is one row, and the same id is its own short Script Property (oypSnap.<id>). Nothing is dropped: a rolling list would forget an old file and queue the QR sticker again. The Settings tab is not created. Drive files are not changed. The two setting rows below are written only when someone saves a checkbox and Settings already has key and value columns.

What the two keys are
  scanner.snap_jewelry    Print jewelry tag    queues kind jewelry_tag (the B1 jewelry tag) after the JO is confirmed
  scanner.snap_qr         Print QR tag         queues kind jo_card (the B31 JO sticker, 30x20, QR on the left) when the scan is filed
  The print queue has those two kinds. There is no third sticker named qr_tag.
  A missing key stays ON. Script Properties hold the values so the 5-minute trigger can read them.
  When the Settings tab already has key and value columns, the same keys are written there and a SettingsLog row is added if that tab exists. The Settings tab is not created.
  Checked jewelry means the confirm step queues the tag. Unchecked jewelry means the confirm step never queues it. Checked QR means the filed scan queues the JO sticker. Unchecked QR means that scan queues no sticker.

Hooks
  1. JoInbox.gs — paste/JoInbox.gs.snapsnap.patch.txt
     Paste both functions at the bottom.
     Call snapPrintAfterFiled_(FILED_JO, SCAN_FILE_ID) after a ScanSnap file has been saved as a new JO. That call queues the QR sticker only.
     Call snapPrintAfterConfirmed_(CONFIRMED_JO) at the end of joInboxConfirm and joInboxFix, after the JO has been written into JobOrders. That is the step that moves a JO READS (check) row, STATUS AUTO or NEEDS CONFIRM, into JobOrders. CONFIRMED_JO is the variable that holds the number just saved. Do not call it before that write, and do not call it from discard, from Send to To review, or from the scan-file path.
     printEnqueue_ then reads JobOrders. A jewelry tag already queued or already printed for that JO is not added again. A failed tag is put back in the queue, which is the queue's existing rule.
  2. PrintQueue.gs — paste/PrintQueue.gs.guess.patch.txt
     Paste the pick() change so a JobOrders cell marked (guess) stays off the tag. Do not replace PrintQueue.gs if you apply that patch. Replacing the whole file with paste/PrintQueue.gs is the same change.
  3. Auth.gs — paste/Auth.gs.snapsnap.patch.txt
     One line so snapPrintGet and snapPrintSet reach ScanSnapPrint. Skip this if that line is already in handleAction_. Without it the page keeps saying changes are not saved yet.

Do not replace JoInbox.gs, Auth.gs, Code.gs, or Settings.gs.
Do not add snapPrintGet or snapPrintSet to Fast.gs or DashCache.gs.
The phone scanner is unchanged. Its JO sticker and Jewelry tag switches, and print_auto_jo_card / print_auto_jewelry_tag, are not these keys.

Then
  Deploy > Manage deployments > pencil > Version: New version > Deploy.
  Do not use New deployment.

A jewelry tag that already printed (including one that went out with only the JO number) is not queued again on confirm. Reprint that JO from the print queue if you want a new tag with the confirmed specs.
